检查规则

规则判定
claimant-missing没有报销人 → error
date-missing没有日期也没有期间 → error
period-unlabelled只有一个日期且没写「报销期间」 → warn
items-missing没有带金额的明细行 → error
total-missing没有合计行 → error
total-mismatch明细相加与合计不符 → error
invoice-duplicate同一发票号出现两次 → error
invoice-missing明细里没有任何发票号 → warn
purpose-missing没有事由说明 → warn
category-missing没有费用类别 → warn
approver-missing没有审批人 → error
currency-mixed多币种且没有汇率说明 → warn

用法

npx dsh-expense-claim-check claim.md --json
npx dsh-expense-claim-check claim.md --tolerance 0.02
npx dsh-expense-claim-check - < claim.md

真实输入输出

输入
报销人：张三
报销期间：2026-11-01 至 2026-11-15

- 高铁票 553.50 元
- 住宿 960.00 元

合计：1600.00 元

$ expense-claim-check claim-sample.md
error total-mismatch 第0行 明细相加是 1513.5，合计行写的是 1600，差 86.5（容差 0.01）——要么抄错，要么有一行没列出来
error approver-missing 第0行 没有审批人（认得：审批人：、批准人：、Approved by）——没有人批过的报销单不该进入付款
warn invoice-missing 第0行 一条发票号都没有（认得：发票号码：12345678）——没有发票号的明细无法在系统里核销
warn purpose-missing 第0行 没有事由说明（认得：事由、用途、Purpose）——只有金额的报销单，审批人无法判断该不该批
fail: 2 items summing 1513.5, total 1600, 2 errors, 2 warnings

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /expense-claim-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
合计那行是这个包的理由：明细相加 1,513.50、合计写 1,600.00 的报销单，页面上看起来完全正常——数字整齐、表格对齐，而合计正是审批人真正读的那个数。差出来的要么是从上一张抄的，要么是往上凑的，两者都不会自己喊。发票号重复同理：一张单子两行、日期不同、号码一样，没有人会去数位数。只看文档，不验这笔钱：同号发票上个月是否已在另一张单子里报过，需要账本，不是一份 Markdown 能回答的。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
