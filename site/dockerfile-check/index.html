检查规则

规则判定
from-missing没有 FROM → error
base-unpinnedFROM node 或 :latest 浮动标签 → error（@sha256 digest 通过）
user-missing没有 USER 指令（默认 root）→ error
user-root显式 USER root 等于没写 → error
secret-in-layerENV/ARG 把疑似密钥写成字面值 → error（${VAR} 引用通过）
add-instead-of-copyADD 普通本地路径 → warn（tar 包与 URL 豁免）
apt-not-cleaned / apk-not-cleaned装完没清理索引 → warn
workdir-missing没有 WORKDIR → warn

用法

npx dockerfile-check Dockerfile --json
npx dockerfile-check Dockerfile --allow-latest --no-require-user

真实输入输出

输入
FROM node
ADD . /app
ENV API_KEY=sk-live-1234567890
CMD ["node", "index.js"]
$ dockerfile-check Dockerfile.sample
error user-missing 第0行 没有任何 USER 指令——容器默认以 root 运行，镜像被拿下就是宿主 root
error base-unpinned 第1行 第 1 行基础镜像「node」没有固定标签或 digest——「node:latest」这类浮动标签让构建不可复现
error secret-in-layer 第3行 第 3 行把疑似密钥「API_KEY」写成了字面值——层历史永久保留，改用构建期 secret 或运行时注入
warn workdir-missing 第0行 没有 WORKDIR——相对路径会落在 /，后续 COPY 的位置容易看错
warn add-instead-of-copy 第2行 第 2 行用的是 ADD 但源不是 URL 也不是压缩包——COPY 语义更窄，读者不用猜
fail: 4 instructions, 3 errors, 2 warnings

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /dockerfile-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
只验文件文本，不验构建出的镜像：它看不见基础镜像里有什么、最终 stage 是不是你要的那个、镜像里到底有没有那个 USER。它验证文件写下了这些决定；镜像行为对不对，靠扫描和实跑。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
