缺陷报告检查清单

它决定一件事：这份 bug 报告是否交代了在哪发生、怎么触发、差在哪。

检查规则

规则判定
title-missing第一行没有 `# 标题` → error
env-missing没有环境信息（## 环境、版本：、OS：、Node：）→ error
repro-missing没有复现步骤标题下的编号步骤 → error
expected-actual-missing预期与实际都没写 → error
expected-missing / actual-missing只写一边 → error，指出缺哪边
repro-thin步骤少于下限（默认 3，可调）→ warn

用法

npx dsh-bug-report-check report.md --json
npx dsh-bug-report-check report.md --min-steps 5

真实输入输出

输入
# 登录按钮在 Safari 下无响应

今天有人反馈说登录不行。
$ bug-report-check bug-sample.md
error env-missing 第0行 没有环境信息（认得：## 环境、版本：x.y.z、OS：…、Node：v…）——没有环境的 bug 无法归因
error repro-missing 第0行 没有复现步骤（认得：## 复现步骤 + 编号步骤）——没有步骤的 bug 无法验证
error expected-actual-missing 第0行 没有「预期」与「实际」的对照（认得：预期：…、实际：…、Expected/Actual）——没有对照就不是 bug 描述
fail: 0 steps, 3 errors, 0 warnings

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /bug-report-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
只验书记层面，不验缺陷严重性：它验证报告说了在哪、怎么复现、差在哪；bug 是否真实存在，靠复现。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
