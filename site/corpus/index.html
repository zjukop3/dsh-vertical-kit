每条规则的语料状况

这里的 29 个检查，判定规则是不是「验证过」，取决于它在多少份真实文档上跑过。自己造的 fixture 只能证明「我想到的情况它判对了」，证明不了「别人写的东西它不会误报」——因为在我编的 fixture 里，「正确」和「被检查器接受」是同一件事。

分三层：跑过陌生人写的文件、跑过自家真实产物、只有自造样例。合计 516 份真实文档。

第三层：只有自造样例（10 个检查）

这些检查的每条规则都在测试里被观察到两个方向——坏文档会报、好文档沉默——但那个「好文档」是我写的。没有陌生人的真实文件跑过它们。

  • agreement-check（合同检查 / 合同审查清单）
  • invoice-check（发票检查 / 发票校验）
  • listing-check（电商商品信息检查 / listing 检查）
  • meeting-notes-check（会议纪要检查 / 会议记录检查）
  • resume-check（简历检查 / 求职简历检查）
  • weekly-report-check（周报检查 / 工作汇报检查）
  • bug-report-check（缺陷报告检查 / bug 报告检查）
  • test-report-check（测试报告检查 / 用例统计检查）
  • handover-check（交接单检查 / 离职交接检查）
  • expense-claim-check（报销单检查 / 费用报销检查）

要补哪一个，看对照表里你手上正好有文件的那一行；脱敏后开一个 语料报告。

为什么第一层最重要

到目前为止找出 24 个检测器缺陷，其中 18 个是拿真实文件跑出来的。这个缺陷在自造 fixture 上永远不会暴露。

最典型的一个是 order 报的行号系统性偏上一行——判定是对的，指针是错的，用户按报的行号找会落在空行上。这件事我写了十几轮都没发现，因为我写 fixture 时只关心「有没有报」，从不关心「报的行号对不对」。第一个陌生人的 changelog 第一次就暴露了它。

另外两处

这套材料不是只有本 kit。同一个作者另两个仓库各有一份：五个通用检查跑过什么（里面记着第 18 个缺陷——tablelint 对故意无表头的表格误报，就是拿第三方 README 试出来的）；以及 项目交接单（唯一维护者写给"如果明天他不在"，接收人一栏至今是「尚未指定」）。
