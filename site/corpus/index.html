每条规则的语料状况

这里的 29 个检查，判定规则是不是「验证过」，取决于它在多少份真实文档上跑过。自己造的 fixture 只能证明「我想到的情况它判对了」，证明不了「别人写的东西它不会误报」——因为在我编的 fixture 里，「正确」和「被检查器接受」是同一件事。

分三层：跑过陌生人写的文件、跑过自家真实产物、只有自造样例。合计 14094 份真实文档。

第三层：只有自造样例（4 个检查）

这些检查的每条规则都在测试里被观察到两个方向——坏文档会报、好文档沉默——但那个「好文档」是我写的。没有陌生人的真实文件跑过它们。

  • agreement-check（合同检查 / 合同审查清单）
    找过：合同：`filename:contract.md` 有 31 万份，但抽样看到的全是**软件契约**（`CONTRACT.md — WP-0 interface contract`、`bundlewatch rewrite contract`、`Data contract: Helios Solar Forecast`），没有一份法律合同；`合同 filename:*.md` 为 0。法律合同在企业内网与 PDF 里，公开 Markdown 形态几乎不存在。
  • invoice-check（发票检查 / 发票校验）
    找过：发票：`filename:invoice.md` 有 8000 份，抽样全是**关于发票的代码文档**（`WebService::Fastly::Object::Invoice` 这类模型文档、ConnectWise 的 invoice cmdlet 文档、OWASP 的 print-invoice 网页），没有一份是真发票；真发票是 PDF/图片。
  • listing-check（电商商品信息检查 / listing 检查）
    找过：商品信息：`filename:listing.md` 有 2.7 万份，抽样是 Chrome Web Store 的 listing 字段、InnerSource 的项目上架说明、多语言商店文案翻译稿——不是电商商品详情。
  • expense-claim-check（报销单检查 / 费用报销检查）
    找过：报销单：`filename:expense-report.md` 只有 108 份，抽样是「如何创建报销单」的文档、agent 提示词模板与 Adaptive Cards 的 sample，不是填过的报销单。

标了「找过」的，是找过但没有找到——不是没找。区别很重要：前者可能是这批文档在公开世界里根本不以 Markdown 存在（发票是 PDF、周报在公司内网），后者只是我还没动手。

要补哪一个，看对照表里你手上正好有文件的那一行；脱敏后开一个 语料报告。

第四层：没有语料，但有出处（4 个检查）

这一组的判据不是从文档里学来的，而是从成文规范里来的。规范也是来源，只是和语料不同类——把它说成语料是自欺，把它藏起来也是。所以单列一层，逐条写出：引的是哪份文件、不检查什么、为什么不引条号。

检查依据不检查
agreement-check《中华人民共和国民法典》合同编对「合同一般条款」的列举（当事人姓名或名称、标的、数量、质量、价款或报酬、履行期限与地点与方式、违约责任、争议解决方式）
引文件而不引条号：条号我没能联网核对，写上去就是第二个「说法与代码不一致」。文件名的列举本身是教科书级共识，可以核对		不判断条款是否合法、是否对我方有利、签署主体是否有权代理——那是律师的活，工具只回答「这八项写了没有」
invoice-checkGB 32100-2015（统一社会信用代码的 18 位字符集，代码里已按它排除了 I/O/S/V/Z）+《中华人民共和国发票管理办法》对发票内容的要求（发票号码、开票日期、金额、购买方与销售方名称及纳税人识别号）

listing-check《中华人民共和国电子商务法》要求经营者全面、真实、准确、及时披露商品信息；《网络交易监督管理办法》要求标明商品名称、规格、价格等信息

为什么没有语料：这四个领域（合同、发票、报销、商品信息）的公开 Markdown 文档里，文件名存在但内容是别的——见每行下面「找过」的那一句。写在规范上并不比写在语料上弱，前提是说清楚是哪一个。

为什么第一层最重要

到目前为止找出 39 个检测器缺陷，来源分布是：22 个来自第三方文件，7 个来自自家真实产物，2 个来自已合并的目录 PR，2 个来自把包装起来调一遍，6 个来自静态审计。这些缺陷在自造 fixture 上永远不会暴露。

最典型的一个是 order 报的行号系统性偏上一行——判定是对的，指针是错的，用户按报的行号找会落在空行上。这件事我写了十几轮都没发现，因为我写 fixture 时只关心「有没有报」，从不关心「报的行号对不对」。第一个陌生人的 changelog 第一次就暴露了它。

另外两处

这套材料不是只有本 kit。同一个作者另两个仓库各有一份：五个通用检查跑过什么（里面记着第 18 个缺陷——tablelint 对故意无表头的表格误报，就是拿第三方 README 试出来的）；以及 项目交接单（唯一维护者写给"如果明天他不在"，接收人一栏至今是「尚未指定」）。
