事故复盘检查清单

它决定一件事：这份复盘是否给出了时间线、影响、根因与有人负责的后续。

检查规则

规则判定
timeline-missing / timeline-entry-untimed没有时间线段，或条目没带时间 → error，报行号
impact-missing没有影响段 → error
root-cause-missing没有根因段 → error
actions-missing / action-no-owner没有后续行动项，或行动项没负责人 → error，报行号
timeline-thin时间线条目少于下限（默认 2）→ warn
duration-missing全文没有时长 → warn

用法

npx incident-report-check postmortem.md --json
npx incident-report-check postmortem.md --min-timeline 4

真实输入输出

输入
# 服务挂了

今天下午服务挂了，重启后恢复了。
$ incident-report-check incident-sample.md
error timeline-missing 第0行 没有时间线（认得：## 时间线 / ## 事件过程 + 带时间的条目）——没有时间的事故报告回答不了「挂了多久」
error impact-missing 第0行 没有影响段（认得：## 影响、影响：…、受影响…）——不知道影响谁的报告无法定级
error root-cause-missing 第0行 没有根因段（认得：## 根因、根本原因：…、root cause）——「重启后恢复」是处置，不是原因
error actions-missing 第0行 没有后续行动项（认得：## 行动项 / ## 后续 + 条目）——没有后续的复盘只写了一份文档
warn duration-missing 第0行 全文没有时长（认得：23 分钟、1 小时、45 秒）——读者要自己拿时间线相减才知道挂了多久
fail: 0 timeline entries, 0 follow-ups, 4 errors, 1 warnings

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /incident-report-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
只验结构，不验根因是否找对：报告可以写一个听起来合理但错误的根因，这个工具分辨不出。它验证文档给出了时间线、影响、原因与有人负责的后续——读者评估分析前需要的四件事。责任归属是人类实践，代码不编码它。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
