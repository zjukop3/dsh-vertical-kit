检查规则

规则判定
type-missing没有 type(scope): subject 前缀 → warn（团队约定；--require-type 才升为 error）
type-unknown类型不在已知集合（feat/fix/docs/…）→ warn
subject-long主题超过上限（默认 72）→ error
subject-empty冒号后没有主题 → error
subject-period主题以句号结尾 → warn
body-separator标题后没有空行 → error
breaking-untrailed用了 ! 但正文没有 BREAKING CHANGE: trailer → warn

用法

npx commit-msg-check .git/COMMIT_EDITMSG --json
npx commit-msg-check msg.txt --max-subject 50
npx commit-msg-check msg.txt --require-type   # 团队用 Conventional Commits 时强制前缀

真实输入输出

输入
修复登录页在弱网环境下偶发超时却没有任何反馈的问题，补上错误文案、重试按钮与失败提示，并新增三条回归测试，覆盖该路径、重试次数上限以及超时之后的状态回收逻辑
$ commit-msg-check commit-sample.txt
error subject-long 第1行 第 1 行主题 78 字，超过 72——git log 会折行，细节放正文
warn type-missing 第1行 第 1 行没有类型前缀（认得：feat/fix/docs/style/refactor/perf/test/build/ci/chore/revert）——「修复登录页在弱网环境下偶发超时却没有任何反馈的问题，补上错误」这条是团队约定，不是 git log 的硬要求——想强制就传 rules.requireType: "error"
fail: type=- subject=78ch, 1 errors, 1 warnings (type policy: warn)

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /commit-msg-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
两类规则不是一回事。「与流派无关」的四条——主题超长、句尾句号、正文前缺空行、! 没有配 trailer——任何仓库、任何语言都是同样地错，所以是 error。「带流派」的一条——类型前缀是 Conventional Commits 的约定，用 `Verb 名词` 写的仓库和中文提交信息没有英文类型词可用，对它们报错不是在挑错，是把自己的规矩套在别人头上；这类默认 warn，要强制传 --require-type。只验信息形状，不验提交内容：diff 是否做了主题说的事，靠评审。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
