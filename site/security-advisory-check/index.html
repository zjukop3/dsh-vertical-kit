检查规则

规则判定
title-missing没有 `# 标题`，也没有 frontmatter 的 title: → error
id-missing没有 CVE / GHSA / 公告编号 → error
severity-missing没有写死的严重程度（严重程度：high）→ error；散文里的「严重」不算
affected-missing没有受影响版本范围，也没写「无」→ error
fixed-missing既没有修复版本，也没写「暂无可用修复」→ error；「建议尽快升级」不算
workaround-missing没有缓解措施或「暂无可用缓解」→ warn，默认不查（--check-workaround 打开）
contact-missing没有报告渠道或致谢 → warn，默认不查（--check-contact 打开）
disclosure-date-missing没有披露日期 → warn

用法

npx dsh-security-advisory-check advisory.md --json
npx dsh-security-advisory-check advisory.md --check-workaround --check-contact

真实输入输出

输入
# 备份导出接口存在越权问题

我们最近发现备份导出接口没有校验归属，任意登录用户可以导出他人的评审包。建议尽快升级。

$ security-advisory-check advisory-sample.md
error id-missing 第0行 没有漏洞编号（认得：CVE-2026-12345、GHSA-xxxx-xxxx-xxxx、公告编号：…）——没有编号的公告无法被检索、被交叉引用
error severity-missing 第0行 没有严重程度（认得：严重程度：high、危险等级：高危、severity: medium）——散文里的「严重」不是等级，无法据此排期
error affected-missing 第0行 没有受影响版本范围（认得：受影响版本 <= 0.1.10、affected < 2.3.0、受影响范围：无）——「早期版本」「修复前」都不算范围，读者无法对照自己的版本
error fixed-missing 第0行 既没有修复版本，也没写「暂无可用修复」（认得：修复版本：0.1.11、fixed in 2.3.1、暂无可用修复）——读者分不清「没修」和「漏写」
warn disclosure-date-missing 第0行 没有披露日期（认得：披露日期：2026-11-18、disclosure date）——没有日期的公告无法判断是新的还是陈年的
fail: severity unstated, 4 errors, 1 warnings

出口码：1。输出为真实 CLI 运行的逐字结果，由测试与工具保持同步。

出口码：0 干净、1 有发现、2 用法或读文件错误。--json 输出机器可读结果。DSH 内同样的函数在 POST /security-advisory-check/api（{"text":"…"} 或 {"path":"…"}），面板与 CI 调同一实现。

这是清单，不是专业人士。合同检查不是法律意见，发票检查不判税务合规，listing 检查不判商业价值。每条发现都是文本里可判定的结构缺陷，带行号。
实测 20 条真实 GHSA 记录：7 条零发现、13 条只报 fixed-missing（那 20 条都没有 patched_versions，其中 13 条正文也没提修复）。缓解与联系渠道默认不查：真实公告里 18/20 与 15/20 都没有，默认报等于噪音。只管公告有没有回答读者的两个问题，不管漏洞是否真实、范围是否正确、等级是否诚实。范围写「<= 0.1.10」不代表这个范围对——那要靠复现和第二双眼睛。也不解析 CVSS 向量、不重算分数。 · dsh-vertical-kit · 通用检查（哈希/引用/结构/表格/数字）在 dsh-verify-kit
